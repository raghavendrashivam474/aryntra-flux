# S3.1 — Shyam Contract → Flux Capability Mapping

## 1. Purpose

Map the Shyam Flux Gateway HTTP contract onto the existing Flux v2.3.0
architecture. Determine what Flux already supports, what needs a thin
adapter, and what capabilities are genuinely missing.

This document is the implementation-ready specification for S3.2
(Flux Gateway Foundation).

### Existing Flux Architecture (untouched)

```text
Discovery (mDNS + UDP heartbeat)
    ↓
PeerRegistry (Vec<Peer>, Arc<RwLock>)
    ↓
PathRegistry (HashMap<PeerId, PathSet>, Arc<RwLock>)
    ↓
PathHealthMonitor<T: Transport>
    ↓
PathProber / PathSelector
    ↓
Session / SessionBuilder<T: Transport>
    ↓
Transport (trait) → TcpTransport
    ↓
TransferManager (stateless, per-call)
```

## 3. Shyam Gateway Contract

The following endpoints are defined by the Shyam project.
Flux does not own this contract; we map onto it.

| # | Method | Path | Purpose |
|---|---|---|---|
| 1 | GET | /flux/v1/identity | Node identity |
| 2 | GET | /flux/v1/status | Runtime status |
| 3 | GET | /flux/v1/peers | Discovered peers |
| 4 | GET | /flux/v1/peers/{peer_id} | Single peer detail |
| 5 | POST | /flux/v1/connect | Establish session |
| 6 | POST | /flux/v1/transfer | Initiate transfer |
| 7 | GET | /flux/v1/transfer/{transfer_id} | Transfer progress |
| 8 | POST | /flux/v1/transfer/{transfer_id}/cancel | Cancel transfer |

## 4. Endpoint-by-Endpoint Mapping

### 4.1 GET /flux/v1/identity

**Shyam intent**: Return the local node's identity.

| Field | Value |
|---|---|
| Existing source | `FluxNode.identity` |
| Existing Flux type | `PeerId(Uuid)` — `crates/flux-core/src/identity/mod.rs` |
| Available fields | `PeerId` wraps a single `Uuid`, implements `Display` |
| Gateway-exposable fields | `peer_id: String` (UUID-v4 string) |
| Missing fields | None |
| Required adapter work | Thin — read `node.identity.to_string()` |

#### Verification from code:

```Rust

// crates/flux-core/src/identity/mod.rs
pub struct PeerId(Uuid);

impl PeerId {
    pub fn new() -> Self { ... }
    pub fn load_or_generate(profile: &str) -> Self { ... }
}

// crates/flux-core/src/node/mod.rs
pub struct FluxNode {
    pub identity: PeerId,  // ← directly accessible
    ...
}
```

> Verdict: ✅ Existing capability. No architecture change.


### 4.2 GET /flux/v1/status

**Shyam intent:** Return high-level Flux runtime status.

| Field                    | Value                                          |
|--------------------------|------------------------------------------------|
| Existing source          | FluxNode.state, FluxNode.registry, FluxNode.path_registry |
| Existing Flux type       | NodeState { Starting, Running, Stopped }     |
| Available fields         | state: NodeState, peer_count: usize (via 
egistry.list().len()), path_count: usize (via path_registry.all_peers().len()) |
| Gateway-exposable fields | status: String, peers_known: u32, paths_tracked: u32 |
| Missing fields           | No DEGRADED state in Flux                    |
| Required adapter work    | **Thin** — read 
ode.state + registry counts |

**Verification from code:**

```rust
// crates/flux-core/src/node/mod.rs
pub enum NodeState {
    Starting,
    Running,
    Stopped,
}

pub struct FluxNode {
    pub identity: PeerId,
    pub registry: PeerRegistry,       // ← .list().len()
    pub path_registry: PathRegistry,  // ← .all_peers().len()
    pub state: NodeState,             // ← direct read
}
```

**DEGRADED semantics note**:

Flux has no `DEGRADED` state. The `NodeState` enum is strictly
`Starting | Running | Stopped`. If the Shyam contract expects a
DEGRADED status (e.g. when paths are unhealthy but the node is
still running), this must be computed by the Gateway adapter
by inspecting `PathRegistry` health — not by modifying `NodeState`.

#### Proposed Gateway representation:

```JSON
{
  "status": "running",
  "peers_known": 3,
  "paths_tracked": 5
}
```

**Information intentionally hidden**:

- Internal transport details
- Discovery mechanism specifics (mDNS vs UDP)
- Individual path health (belongs in /peers/{id})

> Verdict: ✅ Existing capability. Thin adapter for count aggregation.

### 4.3 GET /flux/v1/peers

Shyam intent: List all discovered peers.

| Field | Value |
|---|---|
| Existing source | `FluxNode.registry` → `PeerRegistry` |
| Existing Flux type | `Peer { id: PeerId, address: String, last_seen: Instant }` |
| Available fields | `id`, `address` (primary), `last_seen` |
| Gateway-exposable fields | `peer_id: String`, `address: String`, `last_seen: String` (ISO-8601) |
| Missing fields | `PeerRegistry` stores only one address per peer; multi-path addresses live in `PathRegistry` |
| Required adapter work | Thin — `node.registry.list()` + optional enrichment from `path_registry` |

**Verification from code**:

```Rust
// crates/flux-core/src/peer/mod.rs
pub struct Peer {
    pub id: PeerId,
    pub address: String,      // single primary address
    pub last_seen: Instant,
}

impl PeerRegistry {
    pub fn list(&self) -> Vec<Peer> { ... }
}
```

**Important architectural note**:

`PeerRegistry` is a flat list with one address per peer.
The multi-path addresses are tracked separately in PathRegistry.
The Gateway adapter may optionally enrich the peer list with
path counts from `PathRegistry::get_paths(peer_id)`, but must
not create a duplicate peer registry.

> Verdict: ✅ Existing capability. Thin adapter.

### 4.5 POST /flux/v1/connect

**Shyam intent:** Establish a session with a specific peer.

| Field                    | Value                                          |
|--------------------------|------------------------------------------------|
| Existing source          | PathSelector + SessionBuilder<T: Transport> |
| Existing Flux types      | PathSelector, PathSet, Path, SessionBuilder, Session, TcpTransport |
| Available fields         | PathSelector::select_path(peer_id) → Option<Path>, SessionBuilder::connect(peer_id, addr) → Session |
| Gateway-exposable fields | session_established: bool, peer_id: String, 
emote_addr: String |
| Missing fields           | None for basic connectivity                    |
| Required adapter work    | **Thin** — orchestrate existing path selection + session creation |

**Existing connection flow (verified from code):**

```text
1. PathSelector::select_path(peer_id)
       → reads PathRegistry
       → returns best available Path (deterministic, RTT-based)
2. Extract SocketAddr from selected Path
3. SessionBuilder::new(transport, local_peer_id)
4. SessionBuilder::connect(peer_id, socket_addr)
       → transport.connect(local_peer_id, addr)
       → returns Session { state: Established }
```

**Verification from code**:

```Rust
// crates/flux-core/src/path/selector.rs
impl PathSelector {
    pub fn select_path(&self, peer_id: &PeerId) -> Option<Path> { ... }
}

// crates/flux-core/src/session.rs
impl<'a, T: Transport> SessionBuilder<'a, T> {
    pub fn new(transport: &'a T, local_peer_id: PeerId) -> Self { ... }
    pub async fn connect(&self, peer_id: &PeerId, addr: SocketAddr) -> Result<Session> { ... }
}
```

**Critical architectural constraint**:

The Gateway must not implement its own path selection logic.
No `if tcp_available { ... }` branching. The adapter calls
`PathSelector::select_path()` and trusts Flux's deterministic
selection.

**Gateway adapter pseudocode**:

```Rust
// Gateway does this — nothing more:
let path = PathSelector::new(node.path_registry.clone())
    .select_path(&target_peer_id)
    .ok_or("no available path")?;

let transport = TcpTransport::new();
let builder = SessionBuilder::new(&transport, node.identity.clone());
let session = builder.connect(&target_peer_id, path.remote_addr).await?;
```

> Verdict: ✅ Existing capability. Thin adapter for orchestration.

### 4.6 POST /flux/v1/transfer

**Shyam intent**: Initiate a file/collection transfer to a peer.

| Field | Value |
|---|---|
| Existing source | `TransferManager` (static methods) + `Session` + `TransferPlan` |
| Existing Flux types | `TransferManager`, `TransferPlan`, `TransferItem`, `TransferMetadata`, `Session` |
| Available fields | `TransferManager::send_collection(session, plan)`, `TransferManager::send_file(session, path)` |
| Gateway-exposable fields | `transfer_id: String` (from `TransferMetadata.transfer_id`) |
| Missing fields | No runtime transfer tracking (see gap analysis below) |
| Required adapter work | Moderate — Gateway needs a transfer lifecycle wrapper |

**How Flux currently starts a transfer (verified from code)**:

```text
1. Build TransferPlan from file paths
       → TransferPlan::from_paths(&[PathBuf]) → TransferPlan
2. Establish Session (see 4.5)
3. Call TransferManager::send_collection(&mut session, &plan)
       → iterates plan.items
       → for each item: generates TransferMetadata (with new Uuid)
       → sends TransferRequest → waits for Accept/Resume
       → streams chunks via Chunker
       → sends TransferComplete → waits for TransferResult
4. Returns Result<()> — transfer is done or failed
```

**Verification from code**:

```Rust
// crates/flux-core/src/transfer/manager.rs
pub struct TransferManager;  // ← UNIT STRUCT, no state

impl TransferManager {
    pub async fn send_file(session: &mut Session, file_path: &Path) -> Result<()> { ... }
    pub async fn send_collection(session: &mut Session, plan: &TransferPlan) -> Result<()> { ... }
}

// crates/flux-core/src/transfer/metadata.rs
pub type TransferId = Uuid;  // ← exists, but per-file, ephemeral

pub struct TransferMetadata {
    pub transfer_id: TransferId,  // ← generated in TransferMetadata::new()
    pub file_name: String,
    pub file_size: u64,
    ...
}
```

**⚠️ Architectural gap identified**:

`TransferManager` is a stateless unit struct. It has no registry
of active transfers. The `TransferId` is generated inside
`TransferMetadata::new()` per file, used during the protocol
exchange, and then discarded when `send_file()` returns.

There is no mechanism to:

- Query an in-progress transfer by ID
- Report transfer progress after initiation
- Track multiple concurrent transfers

This is a genuine gap for the Gateway contract, which requires
`GET /transfer/{transfer_id}` to return live progress.

**Proposed resolution** (for S3.2, not S3.1):

**Option A (preferred)**: Gateway-level transfer tracker

- The Gateway adapter wraps `TransferManager` calls
- Maintains a `HashMap<TransferId`, `TransferStatus>` in the Gateway layer
- Updates status as the transfer progresses
- Does NOT modify `TransferManager` itself

**Option B**: Flux-core transfer registry

- Add a `TransferRegistry` to `FluxNode`
- Would require modifying `TransferManager` to accept a registry
- Larger architectural change, needs ADR

**Recommendation**: Option A for S3.2. Revisit Option B if
Shyam requires cross-Gateway transfer visibility.

**Verdict**: ⚠️ Existing transfer capability is functional but
lacks runtime lifecycle tracking. Gateway adapter must provide
a thin tracking wrapper. No Flux-core changes required for S3.2.


### 4.7 GET /flux/v1/transfer/{transfer_id}

**Shyam intent:** Query the progress/status of an active or completed transfer.

| Field                    | Value                                          |
|--------------------------|------------------------------------------------|
| Existing source          | TransferMetadata.transfer_id (Uuid) — exists only during protocol exchange |
| Existing Flux types      | TransferId = Uuid, TransferMetadata, Chunker::progress(), FileReceiver::progress() |
| Available fields         | 	ransfer_id is generated per-file in TransferMetadata::new(). Progress is available as (current_chunk, total_chunks) inside Chunker and FileReceiver during execution |
| Gateway-exposable fields | 	ransfer_id, status, progress_pct, ytes_transferred, ile_name |
| Missing fields           | **No runtime transfer registry exists**         |
| Required adapter work    | **Gateway-level tracking wrapper required**     |

**Investigation result: Case B (from §12 of brief)**

Flux has transfer state but no external-facing lifecycle abstraction.

Detailed findings:

1. **TransferId exists** — pub type TransferId = Uuid in metadata.rs.
   It is generated as Uuid::new_v4() inside TransferMetadata::new().

2. **TransferId is ephemeral** — it is created when send_file_internal()
   builds the metadata, used in protocol messages (TransferRequest,
   TransferChunk, TransferComplete), and then the function returns.
   No reference to the ID is retained after Result<()> is returned.

3. **Progress is internal** — Chunker::progress() → (u32, u32) and
   FileReceiver::progress() → (u32, u32) exist but are scoped to
   the local function call. They are not exposed through any registry.

4. **No concurrent transfer tracking** — TransferManager is a unit
   struct with only static/associated methods. There is no
   HashMap<TransferId, ActiveTransfer> anywhere in the codebase.

**Verification from code:**

```rust
// crates/flux-core/src/transfer/manager.rs
pub struct TransferManager;  // ← no fields, no state

// TransferId is created here and dies when the function returns:
let mut metadata = TransferMetadata::new(file_name, file_size, sha256);
// metadata.transfer_id = Uuid::new_v4()  ← generated
// ... protocol exchange using metadata.transfer_id ...
// function returns Result<()>  ← transfer_id is gone
```

#### Proposed Gateway adapter approach (for S3.2):

```Rust
// Gateway layer — NOT flux-core
struct GatewayTransferTracker {
    active: Arc<RwLock<HashMap<TransferId, TransferStatus>>>,
}

enum TransferStatus {
    Queued,
    InProgress { current_chunk: u32, total_chunks: u32 },
    Completed,
    Failed(String),
    Cancelled,
}
```

The Gateway spawns `TransferManager::send_collection()` in a
background task and updates the tracker as progress events occur.
This requires no changes to `flux-core`.

**Verdict**: 🔴 Genuine capability gap at the Gateway boundary.
No Flux-core modification required. Gateway adapter must provide
a tracking wrapper. See ADR-001 below.

### 4.8 POST /flux/v1/transfer/{transfer_id}/cancel

**Shyam intent**: Cancel an in-progress transfer.

| Field | Value |
| :--- | :--- |
| **Existing source** | None |
| **Existing Flux types** | N/A |
| **Available fields** | N/A |
| **Gateway-exposable fields** | `cancelled: bool` |
| **Missing fields** | No cancellation mechanism exists anywhere |
| **Required adapter work** | Gateway-level cancellation signal + Flux-core cooperative shutdown (future) |

**Investigation result**: Capability missing

**Detailed findings**:

   1. No cancel/stop/abort in `TransferManager` — the transfer loop
      in `send_file_internal()` runs `while let Some((index, data)) = chunker.next_chunk()`
      with no exit condition other than completion or error.

   2. No cancellation in `Session — Session::close()` consumes
      `self` and closes the underlying connection, but there is no
      `Session::cancel()` or cooperative shutdown signal.

   3. No cancellation in protocol — `FluxMessage` variants include
      `TransferRequest`, `TransferAccept`, `TransferResume`, `TransferReject`,
      `TransferChunk`, `TransferComplete`, `TransferResult`, `Goodbye`,
      `Ping`, `Pong`. There is no `TransferCancel` message.

   4. Implicit cancellation exists — dropping the `Session` or
      closing the connection will cause the transfer to fail with an
      I/O error. This is ungraceful but functional.

**Verification from code**:

```Rust
// crates/flux-core/src/transfer/manager.rs — send loop
while let Some((index, data)) = chunker.next_chunk().await? {
    session.send_message(&FluxMessage::TransferChunk { ... }).await?;
    // ← no cancellation check, no break condition
}

// crates/flux-core/src/protocol/message.rs — no TransferCancel variant
// (verified by absence in FluxMessage enum)
```

**Proposed minimal design (for S3.2/S3.3)**:

**Phase 1 (S3.2 — Gateway only)**:

- Gateway drops the session task on cancel request
- Transfer fails with I/O error on the Flux side
- Ungraceful but functional; no Flux-core changes

**Phase 2 (S3.3+ — Flux-core)**:

- Add FluxMessage::TransferCancel { transfer_id } to protocol
- Add cooperative check in TransferManager send/receive loops
- Add Session::shutdown() for graceful close

**Verdict**: 🔴 Genuine capability gap. See ADR-002 below.

## 5. ADR Candidates

### **ADR-001**: Gateway Transfer Lifecycle Tracking

**Status**: Proposed
**Context**: The Shyam Gateway contract requires `GET /transfer/{id}`
to return live transfer progress. Flux's `TransferManager` is stateless
and discards `TransferId` after each transfer completes.

**Decision (proposed)**: Implement a `GatewayTransferTracker` in the
Gateway adapter layer (S3.2). Do not modify `flux-core` transfer
architecture. The tracker wraps `TransferManager` calls in background
tasks and maintains a `HashMap<TransferId`, `TransferStatus>`.

#### **Consequences**:

- No Flux-core changes required
- Transfer tracking is Gateway-scoped (not visible to CLI)
- If cross-Gateway visibility is needed later, revisit with a
  `TransferRegistry` in FluxNode

**Affected modules**: Gateway adapter (new, S3.2)
**Backward compatibility**: Full — no existing APIs change
**Tests required: Gateway tracker unit tests (S3.2)

#### **ADR-002**: Transfer Cancellation Mechanism

**Status**: Proposed
**Context**: The Shyam Gateway contract requires
`POST /transfer/{id}/cancel`. Flux has no cancellation mechanism
at any layer (protocol, session, transfer manager).

**Decision (proposed)**: Two-phase approach.

- Phase 1 (S3.2): Gateway drops the transfer task. Ungraceful but
  functional. No Flux-core changes.
- Phase 2 (S3.3+): Add `TransferCancel` protocol message and
  cooperative shutdown in `TransferManager`.

#### **Consequences**:

- Phase 1: Transfers fail with I/O errors on cancel (acceptable)
- Phase 2: Clean cancellation, but requires protocol version bump
  and changes to FluxMessage, TransferManager, and Session

##### **Affected modules (Phase 2)**:

- crates/flux-core/src/protocol/message.rs
- crates/flux-core/src/transfer/manager.rs
- crates/flux-core/src/session.rs

**Backward compatibility**: Phase 1 — full. Phase 2 — needs
protocol version negotiation.
**Tests required**: Cancellation integration tests (Phase 2)

## 7. Proposed Gateway Integration Point

The Gateway attaches to FluxNode as an external consumer.
It does **not** live inside flux-core.

```text
                Shyam (HTTP)
                    │
            FluxGateway (new crate, S3.2)
                    │
            ┌───────┴───────┐
            │  FluxNode     │
            │  .identity    │  ← /identity
            │  .state       │  ← /status
            │  .registry    │  ← /peers
            │  .path_registry│ ← /peers/{id}, /connect
            └───────┬───────┘
                    │
            PathSelector + SessionBuilder  ← /connect
                    │
            TransferManager (wrapped)      ← /transfer
```

**Recommended crate**: crates/flux-gateway/ (new, S3.2)
**Dependency**: flux-core = { path = "../flux-core" }
**No modifications to**: flux-core, flux-node


## 8. Recommended S3.2 Implementation Scope

1. Create crates/flux-gateway/ with Axum HTTP server
2. Implement read-only endpoints: /identity, /status, /peers, /peers/{id}
3. Implement /connect using PathSelector + SessionBuilder
4. Implement GatewayTransferTracker (ADR-001)
5. Implement /transfer with background task + tracker
6. Implement /transfer/{id} reading from tracker
7. Implement /transfer/{id}/cancel via task abort (ADR-002 Phase 1)
8. Integration tests against a running FluxNode

**Deferred to S3.3+:**
- TransferCancel protocol message (ADR-002 Phase 2)
- TransferRegistry in lux-core
- WebSocket streaming
- Authentication
