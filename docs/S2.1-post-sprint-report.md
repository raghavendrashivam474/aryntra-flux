## 1. Executive Summary

Sprint S2.1 introduces a first-class **path abstraction layer** to Aryntra Flux, enabling the system to represent, discover, and track multiple candidate communication routes between any two peers. This is a **foundational plumbing sprint** — it establishes the data model and discovery integration necessary for future path intelligence (S2.2 measurement, S2.3 relay fallback, S2.4 multiplexing) without introducing any routing heuristics, traffic splitting, or transfer-layer changes.

All 55 existing and new tests pass. Zero protocol changes. Zero regressions in S1.1–S1.6 functionality.

## 3. Architectural Decisions & Rationale

### 3.1 Why a Separate `path` Module Instead of Extending `Peer`

The existing `Peer` struct in `peer/mod.rs` holds a single `address: String` field. We considered expanding it to `addresses: Vec<String>`, but rejected this for three reasons:

1. **Separation of concerns**: A `Peer` answers "who is this node?" A `Path` answers "how do I reach this node?" These have different lifecycles. A peer remains known even when all its paths are `Unavailable`. A path can be revived independently.

2. **Type safety**: Paths carry `TransportKind` and `PathState` metadata that doesn't belong on a peer record. Embedding this in `Peer` would create a struct that conflates identity with reachability.

3. **Forward compatibility**: When S2.3 introduces relay paths and S2.4 introduces multiplexed sessions, the path abstraction will need to grow (e.g., relay metadata, MTU hints, congestion state). Keeping it isolated prevents `Peer` from becoming a god object.

**Decision**: `PathRegistry` lives alongside `PeerRegistry` as a parallel structure. `PeerRegistry` continues to serve legacy consumers. `PathRegistry` serves the new multi-path pipeline.

### 3.2 Why `PathId` Is a UUID, Not a Composite Key

A path is uniquely *identifiable* by the tuple `(PeerId, TransportKind, SocketAddr)`, and we use this tuple for deduplication via `Path::same_route()`. However, the `PathId` itself is an opaque UUID because:

- Composite keys are fragile when fields change (e.g., if a path's remote address changes due to NAT rebinding, is it the same path?).
- UUIDs allow stable references across state transitions.
- Future path types (relay, QUIC) may not have a simple `SocketAddr` component.

The `same_route()` method handles deduplication at the data level; `PathId` handles identity at the reference level.

### 3.3 Why `TransportKind` Is an Enum with a Single Variant

Currently only `TransportKind::Tcp` exists. This is intentional — it establishes the extensibility point without introducing speculative variants. When S2.3 adds relay support or a future sprint adds QUIC, the enum grows by one variant and the `Path` model absorbs it without structural changes.

### 3.4 Why Path State Is Separate from Session State

`PathState` and `SessionState` model different things:

- `PathState` describes the **reachability** of a route (can we get there?).
- `SessionState` describes the **protocol lifecycle** of an active connection (are we handshaken? established? closing?).

A path can be `Available` while its associated session is `Closed` (the route is known-good but no active connection exists). A path can be `Connecting` while a session is in `Handshaking`. Conflating these would create invalid state combinations.

## 4. Implementation Details

### 4.1 New Module: `crates/flux-core/src/path/mod.rs` (~210 lines)

**Types introduced:**

| Type | Purpose |
|---|---|
| `PathId(Uuid)` | Opaque unique identifier for a path |
| `TransportKind` | Enum: currently `Tcp` only |
| `PathState` | Enum: `Discovered`, `Candidate`, `Connecting`, `Available`, `Unavailable` |
| `Path` | Concrete route: `id`, `peer_id`, `transport`, `remote_addr`, `state`, `last_seen` |
| `PathSet` | Per-peer collection with dedup via `same_route()` and state management |
| `PathRegistry` | Thread-safe `Arc<RwLock<HashMap<PeerId, PathSet>>>` |

**Key methods:**

- `Path::same_route(&self, other: &Path) -> bool` — deduplication by `(peer_id, transport, remote_addr)`.
- `PathSet::add_or_update(path)` — inserts new paths or refreshes `last_seen` on duplicates; auto-revives `Unavailable` paths back to `Discovered`.
- `PathSet::set_state(id, state)` — transitions a specific path's lifecycle.
- `PathRegistry::register_path(path)` — thread-safe insertion.
- `PathRegistry::set_path_state(peer_id, path_id, state)` — thread-safe state transition.
- `PathRegistry::get_paths(peer_id) -> Option<PathSet>` — read access.

### 4.2 Modified: `crates/flux-core/src/discovery/mod.rs`

**Change**: The `start_discovery()` function signature expanded from:

```rust
pub fn start_discovery(peer_id: PeerId, registry: PeerRegistry) -> anyhow::Result<()>
```

to:

```rust
pub fn start_discovery(
    peer_id: PeerId,
    registry: PeerRegistry,
    path_registry: PathRegistry,
) -> anyhow::Result<()>
```

**mDNS handler** (lines 30–48): Previously called `info.get_addresses().iter().next()` which discarded all addresses except the first. Now iterates over **all** addresses from `info.get_addresses()`, constructs a `SocketAddr` using `info.get_port()`, and registers each as a `Path` with `TransportKind::Tcp`.

**UDP fallback handler** (lines 80–97): Now registers the sender's IP with `DEFAULT_TCP_PORT` (9000) as a candidate TCP path in addition to updating the legacy `PeerRegistry`.

**Backward compatibility**: Both handlers continue to call `registry.update(Peer { ... })` exactly as before. The `PeerRegistry` update is the first operation in each handler, ensuring legacy consumers see no behavioral change.

### 4.3 Modified: `crates/flux-core/src/node/mod.rs`

**Change**: `FluxNode` now holds a `path_registry: PathRegistry` field, initialized as `PathRegistry::default()` in `FluxNode::new()`. The `start()` method passes `self.path_registry.clone()` to `start_discovery()`.

### 4.4 Modified: `crates/flux-node/src/main.rs`

**Change**: The `Run` command's peer display loop now queries `node.path_registry.get_paths(&peer.id)` for each discovered peer and prints each path's ID, remote address, and state in a tree format:

```

ID: abc123... | Primary: 192.168.1.10
  └── Path [def456...]: 192.168.1.10:9000 (Available)
  └── Path [ghi789...]: 10.0.0.5:9000 (Discovered)
```

### 4.5 Modified: `crates/flux-core/src/lib.rs`

Added `pub mod path;` and re-exports: `Path`, `PathId`, `PathRegistry`, `PathSet`, `PathState`, `TransportKind`.

## 7. Known Limitations & Technical Debt

### 7.1 Path Verification Is Not Automated

S2.1 provides the `set_path_state()` API and the integration test demonstrates manual verification, but there is no background task that automatically probes candidate paths and transitions them to `Available` or `Unavailable`. This is intentional — automated probing requires the measurement infrastructure from S2.2.

**Current state**: Paths enter the registry as `Discovered`. They remain `Discovered` until an external caller (future S2.2 prober) transitions them.

### 7.2 UDP Fallback Port Assumption

The UDP heartbeat fallback registers discovered peers with `DEFAULT_TCP_PORT` (9000) because the UDP beacon only carries the `PeerId`, not the TCP listening port. If a peer listens on a non-default port, the UDP-discovered path will point to the wrong port.

**Mitigation**: mDNS carries the correct port via `ServiceInfo::get_port()`, so mDNS-discovered paths are accurate. The UDP fallback is a resilience mechanism and its paths will be validated (and marked `Unavailable` if incorrect) by S2.2's probing.

### 7.3 No Path Expiry

Paths accumulate in the `PathRegistry` indefinitely. There is no TTL or garbage collection for stale paths. A peer that disappears will leave `Discovered` or `Unavailable` paths in the registry forever.

**Recommendation for S2.2**: Introduce a `last_seen` threshold check in the path prober. Paths not refreshed within N seconds should be evicted or permanently marked `Unavailable`.

### 7.4 `Peer.address` Remains Single-Valued

The legacy `Peer` struct still holds a single `address: String`. The `Run` command displays it as "Primary" alongside the full path listing. This is acceptable for S2.1 but should be revisited if any legacy code path depends on `Peer.address` being the "best" address.

## 8. Integration Points for S2.2

S2.2 (Path Measurement & Auto-Selection) can build directly on S2.1's output:

1. **Input**: `PathRegistry::get_paths(peer_id)` returns all candidate paths. S2.2's prober iterates over `Discovered` and `Candidate` paths.

2. **Probing**: For each candidate, establish a `Session` via `SessionBuilder::connect()`, measure RTT via `Ping`/`Pong` round-trips, then close the session. Transition the path to `Available` or `Unavailable` via `PathRegistry::set_path_state()`.

3. **Selection**: Once paths have measurement metadata (stored as new fields on `Path` or in a parallel `PathMetrics` struct), S2.2 can introduce a `select_best_path(peer_id) -> Option<&Path>` method on `PathRegistry`.

4. **Session reuse**: S2.2 may want to keep verified sessions alive rather than closing them after probing. This would require extending `Path` to optionally hold an active `Session` reference — a design decision for S2.2.

## 10. Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Path registry memory growth from stale entries | Medium | Low | S2.2 prober should implement TTL eviction |
| UDP fallback paths pointing to wrong port | Medium | Low | mDNS paths are authoritative; UDP paths validated by S2.2 probing |
| `PathRegistry` lock contention under high peer counts | Low | Medium | `RwLock` allows concurrent reads; write only on discovery events |
| `TransportKind` enum growth causing match exhaustiveness churn | Low | Low | Standard Rust pattern; new variants are additive |

## 11. Recommendations

1. **Proceed to S2.2 immediately.** The path model is stable, tested, and ready for measurement integration. No architectural rework is needed.

2. **Consider adding `PathMetrics` in S2.2** as a separate struct attached to `Path` (e.g., `rtt_ms: Option<u64>`, `throughput_bps: Option<u64>`, `last_probed: Option<Instant>`). This keeps measurement data out of the core identity model established in S2.1.

3. **Defer `Peer.address` deprecation** until S2.3 or later. It still serves as a quick-access "primary" address for legacy code paths and CLI display.

4. **Add path expiry in S2.2** as part of the prober's background loop. A simple `Instant::elapsed() > Duration::from_secs(300)` check on `last_seen` would prevent unbounded registry growth.

## 12. Conclusion

S2.1 delivers exactly what the S1.6 post-sprint report specified: a multi-path foundation that answers **"What paths exist?"** without prematurely answering **"Which path is best?"** The implementation is minimal, well-tested, fully backward-compatible, and provides clean integration seams for S2.2's measurement and selection work.

The codebase is ready for the next evolution.
