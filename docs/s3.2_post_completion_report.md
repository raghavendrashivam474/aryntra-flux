## 1. Executive Summary

Sprint S3.2 delivered the **Flux Gateway Foundation** — a new crate (`crates/flux-gateway/`) that exposes all 8 Shyam-contract HTTP endpoints over `127.0.0.1:9100` using Axum 0.7. The Gateway acts as a thin, read-mostly adapter over the existing `flux-core` runtime. No modifications were made to `flux-core`'s networking, transport, discovery, session, or transfer subsystems.

### 2.2 Endpoint Implementation Details

**GET `/flux/v1/identity`**
- Reads `FluxNode.identity` directly. `PeerId` implements `Display`, so the response is `{ "peer_id": "<uuid-v4>" }`.
- Adapter complexity: trivial (one-liner).

**GET `/flux/v1/status`**
- Reads `FluxNode.state` (mapped to lowercase string), `registry.list().len()`, and `path_registry.all_peers().len()`.
- Returns `{ "status": "running", "peers_known": N, "paths_tracked": M }`.
- DEGRADED semantics are **not** implemented — see Section 4.3.

**GET `/flux/v1/peers`** and **GET `/flux/v1/peers/{peer_id}`**
- Calls `PeerRegistry::list()` which returns `Vec<Peer>`.
- Each `Peer` is mapped to `{ "peer_id", "address", "last_seen_secs_ago" }`.
- `last_seen` is a `std::time::Instant`, converted to elapsed seconds for JSON serialization.
- Single-peer lookup performs a linear scan with `404 PEER_NOT_FOUND` on miss.

**POST `/flux/v1/connect`**
- Parses `peer_id` from the JSON body as a UUID string.
- Reconstructs a `PeerId` via `serde_json::from_str::<PeerId>(...)` for registry lookups.
- Validates the peer exists in `PeerRegistry`.
- Instantiates a `PathSelector` from the node's `PathRegistry` and attempts optimal RTT-based path selection.
- Falls back to the peer's primary `address` field if no probed path with metrics is available.
- Builds a `SessionBuilder` using the Gateway's own `TcpTransport` and calls `.connect()`.
- Stores the established `Session` in a thread-safe `Arc<Mutex<HashMap<String, Session>>>` session pool keyed by peer ID.

**POST `/flux/v1/transfer`**
- Extracts the `Session` from the pool (removing it to prevent concurrent use).
- Builds a `TransferPlan` from the requested file paths using `TransferPlan::from_paths()`.
- Computes `total_bytes` by reading file metadata asynchronously.
- Spawns a background `tokio::spawn` task that calls `TransferManager::send_collection()`.
- Registers the transfer in `GatewayTransferTracker` with the task handle for cancellation.
- Returns immediately with `{ "transfer_id": "<uuid>", "status": "RUNNING" }`.

**GET `/flux/v1/transfer/{transfer_id}`**
- Queries `GatewayTransferTracker` for the current lifecycle state.
- Returns full `GatewayTransferInfo` including progress counters and status.

**POST `/flux/v1/transfer/{transfer_id}/cancel`**
- Phase 1 implementation: calls `task_handle.abort()` on the spawned transfer task.
- Marks the transfer as `CANCELLED` in the tracker.
- Does **not** implement protocol-level cancellation (deferred to S3.3+ per ADR-002).

### 2.3 Transfer Tracker Architecture

The `GatewayTransferTracker` is a `Clone`-able wrapper around `Arc<RwLock<HashMap<String, ActiveTransfer>>>`. Each `ActiveTransfer` holds:

- `GatewayTransferInfo` (serializable state: status, bytes, files, timestamps)
- `Option<JoinHandle<()>>` (the spawned transfer task, used for Phase 1 cancellation)

Lifecycle states: `CREATED → RUNNING → COMPLETED | FAILED | CANCELLED`.

## 3. How Key Decisions Were Made

### 3.1 Dependency Direction

The single most important architectural constraint was enforced from the start:

```
flux-gateway → flux-core    ✅
flux-core → flux-gateway    ❌ (never)
```

`flux-core`'s `Cargo.toml` was not touched. The Gateway depends on `flux-core` via a path dependency.

### 3.2 Transport Ownership

`FluxNode` is transport-agnostic — it does not own a `TcpTransport`. The transport is instantiated at the call site (as seen in `flux-node/src/main.rs`). The Gateway follows the same pattern: `GatewayState` owns an `Arc<TcpTransport>` created at startup.

### 3.3 Session Pool Design

Since `TransferManager::send_collection()` requires `&mut Session`, sessions cannot be shared concurrently. The Gateway uses a take-and-return pattern:

1. `/connect` inserts the session into the pool.
2. `/transfer` removes it (`.remove()`) for exclusive use.
3. A `SessionReturnGuard` with a custom `Drop` implementation guarantees the session is returned to the pool when the transfer task completes, fails, panics, or is aborted.

### 3.4 HTTP Framework Selection

Axum 0.7 was chosen because:
- It is the most widely adopted async Rust HTTP framework.
- It integrates natively with Tower middleware (tracing, CORS).
- It uses `State` extractors that map cleanly to our `GatewayState` clone pattern.
- It resolved without version conflicts against the existing Tokio 1.x dependency.

## 4. Problems Faced and Mitigations

### 4.1 Incorrect Field Assumptions on Core Types

**Problem:** The initial route implementations assumed `FluxNode` had fields like `node.identity.peer_id`, `node.identity.name`, and `node.peers`. The actual structure is:

```rust
pub struct FluxNode {
    pub identity: PeerId,        // PeerId IS the identity (UUID newtype)
    pub registry: PeerRegistry,  // NOT "peers"
    pub path_registry: PathRegistry,
    pub state: NodeState,
}
```

Additionally, `Peer` has `address: String` (singular), not `addresses: Vec<String>`, and no `name` field.

**Mitigation:** Inspected `crates/flux-core/src/node/mod.rs`, `identity/mod.rs`, and `peer/mod.rs` directly. Rewrote all route handlers to match the actual public API. Used `node.identity.to_string()` for the peer ID, `node.registry.list()` for peer enumeration, and mapped `peer.address` as a single string.

### 4.2 Lock Type Mismatch (tokio vs std)

**Problem:** The initial `GatewayState` wrapped `FluxNode` in `Arc<tokio::sync::RwLock<FluxNode>>`. However, `PeerRegistry` and `PathRegistry` internally use `std::sync::RwLock` with synchronous `.read().unwrap()` calls. Wrapping the entire node in an async lock was unnecessary and created an impedance mismatch.

**Mitigation:** Changed `GatewayState` to hold `Arc<FluxNode>` directly. Since the registries are already `Arc<RwLock<...>>` internally and `Clone`-able, sharing the node via `Arc` is sufficient. No async lock is needed at the Gateway level for read operations.

### 4.3 UTF-8 Encoding Corruption from PowerShell

**Problem:** Writing `connect.rs` via PowerShell's `Set-Content` introduced invalid UTF-8 bytes. An em-dash character (`—`) in a comment was encoded as a multi-byte sequence that `rustc` rejected:

```
error: couldn't read `crates\flux-gateway\src\routes\connect.rs`: stream did not contain valid UTF-8
note: byte `151` is not valid utf-8
```

**Mitigation:** Switched all file writes to `[System.IO.File]::WriteAllText($path, $content, [System.Text.Encoding]::UTF8)` which guarantees clean UTF-8 output. Replaced all non-ASCII characters in comments with plain ASCII equivalents.

### 4.4 PeerId Reconstruction from String

**Problem:** The `/connect` endpoint receives a `peer_id` as a UUID string in the JSON body. However, `PeerId` is a newtype around `Uuid` with no public `from_str` or `from_uuid` constructor. The only public constructors are `PeerId::new()` (random) and `PeerId::load_or_generate(profile)` (disk-backed).

**Mitigation:** Leveraged the fact that `PeerId` derives `Serialize` and `Deserialize`. Reconstructed the `PeerId` via:

```rust
let target_uuid = uuid::Uuid::parse_str(&payload.peer_id)?;
let target_peer_id = serde_json::from_str::<PeerId>(&format!("\"{}\"", target_uuid))?;
```

This is a pragmatic workaround. A future improvement would be to add `impl FromStr for PeerId` in `flux-core`, but that was out of scope for S3.2 per the "do not modify core" constraint.

### 4.5 No DEGRADED State in NodeState

**Problem:** The S3.1 mapping noted that the Shyam contract may expect a `DEGRADED` status, but `NodeState` only has `Starting | Running | Stopped`.

**Mitigation:** Per the S3.1 recommendation, the Gateway does **not** modify `NodeState`. The `/status` endpoint returns the raw state string. If DEGRADED semantics are needed in the future, they should be derived at the Gateway layer by inspecting `PathRegistry` health metrics (e.g., ratio of `Unavailable` paths to total paths). This was documented as a future enhancement rather than implemented speculatively.

### 4.6 Session Mutability and Transfer Exclusivity

**Problem:** `TransferManager::send_collection()` takes `&mut Session`, meaning a session cannot be used for multiple concurrent transfers. Naively holding a lock on the session pool during the entire transfer would block all other operations.

**Mitigation:** Implemented a take-and-return pattern. The transfer route `.remove()`s the session from the pool, runs the transfer in a background task, and returns the session via a `SessionReturnGuard` that implements `Drop`. This ensures:
- No concurrent access to the same session.
- The session is returned even if the task panics or is aborted.
- The pool lock is held only for the duration of the `.remove()` call, not the entire transfer.

### 4.7 Clippy Strict Mode Failures

**Problem:** Running `cargo clippy -- -D warnings` caught a lazy evaluation issue:

```
error: unnecessary closure used to substitute value for `Option::None`
  --> crates/flux-gateway/src/routes/transfer.rs:143
  help: use `ok_or` instead of `ok_or_else`
```

**Mitigation:** Replaced `.ok_or_else(|| GatewayError::TransferNotFound(transfer_id))` with `.ok_or(GatewayError::TransferNotFound(transfer_id))` since the error value is cheap to construct.

## 5. What Was NOT Implemented (Intentional Deferrals)

| Item | Reason | Target Sprint |
|---|---|---|
| Protocol-level transfer cancellation | Requires `TransferCancel` message, session shutdown protocol, cooperative cancellation loop | S3.3+ (per ADR-002) |
| DEGRADED status derivation | Requires agreed-upon health threshold semantics with Shyam team | S3.3+ |
| WebSocket streaming for transfer progress | Out of S3.2 scope per the brief | Future |
| Authentication / TLS | Out of S3.2 scope; localhost-only for now | Future |
| `impl FromStr for PeerId` in flux-core | Would require core modification; worked around via serde | S3.3+ candidate |
| Transfer progress byte-level updates | `TransferManager` does not expose mid-transfer progress callbacks | Requires core enhancement |
