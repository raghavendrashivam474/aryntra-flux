## 1. Executive Summary

S3.1 was an **architecture-mapping sprint**, not an implementation sprint. The objective was to determine, endpoint-by-endpoint, how the pre-defined Shyam Flux Gateway HTTP contract maps onto the existing Flux v2.3.0 architecture — and to identify, without speculation, exactly what already exists, what needs a thin adapter, and what represents a genuine architectural gap.

The output is a single 680-line document (`docs/S3.1-shyam-contract-mapping.md`) containing the implementation-ready specification for S3.2 (Flux Gateway Foundation).

**Key result:** 6 of 8 Shyam endpoints map directly onto existing Flux capabilities with thin adapters. 2 endpoints (`/transfer/{id}` and `/transfer/{id}/cancel`) represent genuine gaps, both of which can be resolved at the Gateway layer without modifying `flux-core`, per ADR-001 and ADR-002.

**Zero modifications were made to any existing Flux subsystem.** The v2.3.0 test suite (74 tests) remains green. `fmt` and `clippy` remain clean.

## 5. Findings — Endpoint by Endpoint

### 5.1 Direct-mapping endpoints (6 of 8)

| Endpoint | Backing Flux Capability | Adapter |
|---|---|---|
| `GET /identity` | `FluxNode.identity` → `PeerId(Uuid)` | Thin |
| `GET /status` | `FluxNode.state` (`NodeState` enum) + registry counts | Thin |
| `GET /peers` | `PeerRegistry::list()` → `Vec<Peer>` | Thin |
| `GET /peers/{id}` | `PathRegistry::get_paths()` → `PathSet` | Thin |
| `POST /connect` | `PathSelector::select_path()` + `SessionBuilder::connect()` | Thin |
| `POST /transfer` | `TransferManager::send_collection()` | Moderate (tracker wrapper) |

For these six, no `flux-core` changes are required. The Gateway simply reads existing state or invokes existing methods.

### 5.2 Gap endpoints (2 of 8)

**`GET /transfer/{transfer_id}`** — Case B under §12 of the brief.

`TransferId` exists (`pub type TransferId = Uuid` in `transfer/metadata.rs`), but it is generated inside `TransferMetadata::new()` per file, used during the protocol exchange, and discarded when `TransferManager::send_file_internal()` returns. `TransferManager` itself is a **stateless unit struct** (`pub struct TransferManager;` with only associated functions — no fields, no registry).

There is no mechanism to query an in-progress transfer, report progress externally, or track concurrent transfers.

**`POST /transfer/{transfer_id}/cancel`** — capability entirely missing.

- No cancel/stop/abort method in `TransferManager`
- No `TransferCancel` variant in `FluxMessage`
- No cooperative shutdown check in the send/receive loops (the loop is `while let Some((index, data)) = chunker.next_chunk().await?` with no cancellation branch)
- No `Session::cancel()` — only `Session::close()` which consumes `self`

Implicit cancellation exists (drop the session, transfer fails with I/O error), but this is ungraceful.

## 6. Problems Faced and How They Were Mitigated

### Problem 1 — Ambiguity about what counts as an "existing capability"

**Issue:** The brief was strict: *"Do not mark something 'existing' merely because something similar exists. Verify it from the implementation."* Early in Phase 2 I was tempted to mark `TransferId` as sufficient support for `GET /transfer/{id}` because the type exists.

**Mitigation:** I enforced a rule that every "existing" verdict required a direct code citation showing the type is (a) accessible from outside the module and (b) retains state after the initiating call returns. This is what surfaced the `TransferManager` statelessness issue — the type exists, but the runtime instance does not persist. I reclassified `/transfer/{id}` from "existing" to "gap" as a result.

### Problem 2 — PowerShell directory-object enumeration

**Issue:** During Phase 2, `Get-ChildItem crates/flux-core/src/node*` returned the *directory* `node` as an object, which was then passed to `Get-Content`, producing:
```
Get-Content : Access to the path '...\node' is denied.
```

**Mitigation:** Reran the inspection with `-File -Filter "*.rs"` and an explicit `if (Test-Path ...)` guard in a helper function. All subsequent blocks used the guarded pattern. No data was lost — only the initial inspection command had to be rerun.

### Problem 3 — Truncated output during deep inspection

**Issue:** Block 3 (full-file dump of ~10 files) produced enough output that some content scrolled beyond what I could reliably capture in a single review — specifically, the full `FluxNode` struct definition was cut off.

**Mitigation:** Added a targeted follow-up block (Block 4) that re-ran `Get-Content` on `node/mod.rs` and `path/mod.rs` only, with context lines around `NodeState` and `PathState` patterns. This confirmed:
- `NodeState = Starting | Running | Stopped` (no `Degraded`)
- `PathState = Discovered | Candidate | Connecting | Available | Unavailable`
- `FluxNode` owns exactly four fields: `identity`, `registry`, `path_registry`, `state`

This directly informed the "DEGRADED semantics" note in section 4.2 of the document, flagging that the Gateway must synthesize any `DEGRADED` status by inspecting `PathRegistry` — it cannot come from `NodeState`.

### Problem 4 — Temptation to design the fix during analysis

**Issue:** Once the transfer-tracking gap was identified, the natural impulse was to sketch out a `TransferRegistry` inside `flux-core`. The brief explicitly forbids this in §15: *"Do not silently alter architecture."*

**Mitigation:** I split the resolution into two options in ADR-001:
- **Option A (preferred):** Gateway-level `GatewayTransferTracker` — zero `flux-core` changes
- **Option B:** `TransferRegistry` in `FluxNode` — flagged as a larger change requiring its own ADR if ever pursued

Option A was recommended for S3.2. This preserves the architectural boundary the brief demanded: *"Flux does not lose ownership of its own networking architecture."*

Similarly for cancellation (ADR-002), I proposed a two-phase approach:
- **Phase 1 (S3.2):** Gateway drops the task — ungraceful but functional, zero `flux-core` changes
- **Phase 2 (S3.3+):** Add `TransferCancel` protocol message and cooperative shutdown — requires protocol version negotiation, deferred

### Problem 5 — Document sprawl risk

**Issue:** The original plan was to generate the entire mapping document in one commit. Given the density of the content (8 endpoints, 2 ADRs, code citations for each), this risked producing an unreviewable monolith.

**Mitigation:** Built the document incrementally in five patches:
1. Header + `/identity`
2. `/status` + `/peers` + `/peers/{id}`
3. `/connect` + `/transfer`
4. `/transfer/{id}` + `/transfer/{id}/cancel` + ADRs
5. Capability table + integration point + S3.2 scope + non-goals + DoD

Each patch was line-counted after append to confirm the file grew as expected. The final document is 680 lines and structurally follows §17 of the brief exactly.

## 7. Architectural Decisions Recorded

### ADR-001 — Gateway Transfer Lifecycle Tracking

**Decision:** Implement `GatewayTransferTracker` in the Gateway adapter layer (S3.2). Do not modify `flux-core`.

**Rationale:** `TransferManager` is stateless by design. Adding a registry to it would alter the transfer subsystem's ownership model. The Gateway is the natural place to track HTTP-visible transfer state because it is the only consumer that needs cross-request visibility.

**Consequences:** Transfer tracking will be Gateway-scoped, not visible to the CLI. If cross-consumer visibility is ever required, we revisit with a `TransferRegistry` in `FluxNode` — but only then, and only with a new ADR.

### ADR-002 — Transfer Cancellation Mechanism

**Decision:** Two-phase approach.
- **Phase 1 (S3.2):** Gateway aborts the transfer task. Transfer fails with I/O error on the Flux side. Ungraceful but functional. Zero `flux-core` changes.
- **Phase 2 (S3.3+):** Add `FluxMessage::TransferCancel { transfer_id }`, cooperative check in send/receive loops, `Session::shutdown()`. Requires protocol version bump.

**Rationale:** The Shyam contract requires *a* cancel endpoint. Phase 1 satisfies the contract behaviorally. Phase 2 is the correct long-term fix but requires touching the protocol, which is a significant enough change to warrant its own sprint.

## 11. Recommendations for S3.2

1. **Create `crates/flux-gateway/` as a new crate** with `flux-core = { path = "../flux-core" }` and no reverse dependency. The Gateway must be a pure consumer.

2. **Implement the six direct-mapping endpoints first.** They are low-risk and will produce a working read-only Gateway within days.

3. **Implement `GatewayTransferTracker` before `POST /transfer`.** The tracker is the foundation for both `/transfer` and `/transfer/{id}`, and it is the only non-trivial piece of new architecture in S3.2.

4. **Ship Phase 1 cancellation (task abort) in S3.2.** Do not attempt Phase 2 (protocol-level cancellation) inside S3.2 even if time permits — the protocol change deserves its own sprint and version-negotiation design.

5. **Add a `NodeHandle` or similar shared-state abstraction** if the current `FluxNode` ownership model (currently owned by `main.rs`) makes it awkward to hand to the Gateway. This is a `flux-node` concern, not `flux-core`, and should be discussed before starting S3.2.

## 12. Open Questions for Senior Review

1. **DEGRADED status semantics.** The Shyam contract may or may not require a `DEGRADED` state. Flux's `NodeState` has no such variant. The document proposes synthesizing it in the Gateway from `PathRegistry` health. Please confirm whether this is aligned with the Shyam-side expectation.

2. **ADR-001 Option A vs Option B.** I recommended Option A (Gateway-scoped tracker). If there is a foreseeable requirement for the CLI or a second consumer to also see transfer state, Option B (Flux-core `TransferRegistry`) becomes more attractive. Please advise.

3. **ADR-002 Phase 2 timing.** Phase 1 (task abort) is functional but ungraceful. If graceful cancellation is a hard requirement for the initial Shyam integration, Phase 2 needs to be pulled forward into S3.2 or S3.2.5, and the protocol version negotiation strategy needs to be designed first.
