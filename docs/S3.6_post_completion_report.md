## 1. Executive Summary

S3.6 delivers **autonomous path-aware transfer migration** to Flux. Prior to this sprint, when the underlying session/path of an active transfer failed, the entire transfer aborted and the caller was responsible for manually detecting the failure, selecting a new path, establishing a replacement session, and invoking `continue_collection` with a `TransferContinuation`. S3.5 provided the primitives for cross-session continuity but required explicit caller orchestration.

S3.6 closes that gap. A transfer running through the new `TransferCarrier` abstraction now:

1. **Detects** carrier failure via `TransferError::Transport(_)` surfacing from the session layer.
2. **Checkpoints** verified progress to the last fully-completed file boundary using the authoritative `TransferProgress` tracker.
3. **Marks** the failed path as `Unavailable` in `PathRegistry`.
4. **Selects** the next optimal alternate path via the existing deterministic `PathSelector`.
5. **Establishes** a replacement `Session` through `SessionBuilder`.
6. **Resumes** chunk transmission from the exact point of interruption using the receiver's existing `TransferResume` protocol — no new wire messages introduced.
7. **Completes** the transfer with full SHA-256 integrity verification intact.

The central architectural principle — **Transfer ≠ Path**, where paths and sessions are replaceable carriers of a durable logical transfer operation — is now enforced in code and verified by end-to-end tests.

## 2. What Was Implemented

### 2.1 Migration State Machine (`crates/flux-core/src/transfer/migration.rs`)

A new module introducing two primary types:

**`MigrationState` enum** — makes the carrier lifecycle explicit, observable, and testable:

```
Active { path_id }
    │
    │ carrier failure
    ▼
Migrating { from_path, to_path, attempt }
    │
    ├─── alternate found ──→ Active { new_path_id }
    │
    └─── no alternate ─────→ Paused { reason }

Terminal states: Completed, Failed { reason }
```

**`TransferCarrier<T: Transport>` struct** — the path-aware carrier wrapping an active session:

```rust
pub struct TransferCarrier<T: Transport> {
    pub peer_id: PeerId,
    pub current_path_id: PathId,
    pub session: Session,
    pub registry: PathRegistry,
    pub transport: Arc<T>,
    pub local_peer_id: PeerId,
    pub state: MigrationState,
    pub migration_count: usize,
}
```

The core method `migrate(&mut self) -> Result<()>` performs the complete migration sequence:
1. Marks `current_path_id` as `PathState::Unavailable` via `registry.set_path_state()`.
2. Transitions state to `Migrating { from_path, to_path: None, attempt }`.
3. Gracefully shuts down the dead session via `session.shutdown()`.
4. Invokes `PathSelector::select_path(&peer_id)` to find the next-best candidate.
5. If no candidate exists → transitions to `Paused { reason }` and returns an error.
6. If a candidate exists → connects via `SessionBuilder::connect()`.
7. On successful connection → updates `current_path_id`, replaces `session`, transitions to `Active { path_id }`.
8. On connection failure → marks the candidate `Unavailable` and transitions to `Failed { reason }`.

### 2.2 Carrier-Driven Transfer Orchestration (`crates/flux-core/src/transfer/manager.rs`)

Two new entry points added to `TransferManager`:

- `send_file_with_carrier<T>(carrier, file_path, cancel, progress)` — single-file convenience wrapper that builds a one-item plan.
- `send_collection_with_carrier<T>(carrier, plan, cancel, progress)` — the core migration-aware transfer loop.

The loop maintains `current_idx = progress.files_completed()` as the authoritative resume cursor and handles errors as follows:

| Error | Handling |
|---|---|
| `Ok(())` | Increment `current_idx`, call `progress.add_file()` |
| `TransferError::Cancelled` | Propagate immediately |
| `TransferError::Transport(_)` | Calibrate progress to verified baseline, invoke `carrier.migrate()`, retry current file on new session |
| Other errors | Propagate |

On successful completion, the loop sends `FluxMessage::Goodbye` and sets `carrier.state = MigrationState::Completed`.

### 2.3 Public API Surface (`crates/flux-core/src/lib.rs`)

Re-exported new types alongside existing transfer primitives:

```rust

    CollectionError, MigrationState, TransferCancellation, TransferCarrier,

```

7. S3.5 E2E tests (`test_e2e_transfer_continues_on_alternate_path`, `test_e2e_multi_file_transfer_continues_on_alternate_path`) — understood the test pattern of two listeners (A and B) with controlled chunk-count behavior to simulate failure.
8. Gateway `transfer_tracker.rs` and `routes/transfer.rs` — confirmed the Gateway's `SessionReturnGuard` pattern and `attach_continuation()` method, ensuring any new carrier API would not disturb the existing adapter boundary.

## 4. Problems Encountered & Mitigations

### Problem 1: `TransferManager` is a stateless utility struct

**Observation:** `TransferManager` was defined as `pub struct TransferManager;` — a zero-sized type with only associated functions. There was no instance to hold migration state, no field to attach a path registry or carrier reference.

**Mitigation:** Introduced the migration state and path-awareness as an **external carrier** (`TransferCarrier<T>`) that the caller constructs and passes into the new `send_collection_with_carrier` method as `&mut`. This preserves the stateless nature of `TransferManager` (consistent with its existing design) while giving the migration state a well-defined owner. No existing method signatures were modified.

### Problem 2: PowerShell string-replacement for inserting Rust methods into `manager.rs`

**Observation:** My initial attempts to append the two new carrier methods to `manager.rs` using `$rawCode.Replace($targetMarker, $replacement)` resulted in the methods being inserted **outside** the `impl TransferManager` block — placing them at module scope after `fn hex_encode`. The compiler correctly rejected this with `expected one of ., ;, ?, }, or an operator, found doc comment`.

**Mitigation:**
1. First reverted the file cleanly with `git checkout crates/flux-core/src/transfer/manager.rs`.
2. Switched from heredoc-string-replacement to a **line-based insertion algorithm**: read the file as an array of lines, located the line containing `fn hex_encode`, walked backward to find the closing `}` of `impl TransferManager`, and inserted the new methods immediately before that brace. This surgical approach eliminated all whitespace/CRLF matching ambiguities.
3. Re-ran `cargo clippy` — clean.

### Problem 3: Incorrect `PathRegistry` method name

**Observation:** My initial `migration.rs` called `self.registry.update_state(...)` which does not exist on `PathRegistry`. Compilation failed with `no method named 'update_state' found for struct 'PathRegistry'`.

**Mitigation:** Inspected `crates/flux-core/src/path/mod.rs` directly and discovered the correct API is `set_path_state(peer_id, path_id, state)` which takes **three** arguments (the registry is keyed by `PeerId` → `PathSet`). Updated both call sites in `migrate()`. This also led me to use the correct test assertion pattern: `registry.get_paths(&peer_id).unwrap().get(&path_id).unwrap().state` rather than a nonexistent `get_path()` helper.

### Problem 4: Incorrect `TransportError` variant name

**Observation:** My mock `Transport::listen()` in the unit tests used `TransportError::IoError(...)` which does not exist. The actual variant is `Io(#[from] io::Error)`.

**Mitigation:** Inspected `crates/flux-core/src/transport/error.rs`, corrected the variant to `TransportError::Io(...)`.

### Problem 5: Clippy warning on `std::io::Error::new` with `ErrorKind::Other`

**Observation:** After fixing Problem 4, clippy flagged the construction as `clippy::io_other_error`, recommending the newer idiomatic `std::io::Error::other()`.

**Mitigation:** Replaced `std::io::Error::new(std::io::ErrorKind::Other, "unsupported")` with `std::io::Error::other("unsupported")` in the mock. Clippy clean.

### Problem 6: Unused imports after initial manager.rs edits

**Observation:** Because the insertion of the new methods initially placed them outside the `impl` block, `MigrationState`, `TransferCarrier`, and `Transport` were imported but unused — generating warnings that failed `clippy -D warnings`.

**Mitigation:** Resolved automatically once Problem 2 was fixed and the methods were correctly placed inside `impl TransferManager`, making all imports necessary and consumed.

### Problem 7: Baseline commit mismatch

**Observation:** The brief specified baseline commit `788c109`, but the actual HEAD on the local clone was `78fe571`. Initial reaction was concern that we were on the wrong baseline.

**Mitigation:** Verified via `git tag -l "v0.15.0"` that the `v0.15.0` tag existed on the current HEAD. The `788c109` short-hash in the brief was from a prior clone's history (likely before a rebase or amend); the tag `v0.15.0` is the canonical identity marker. Confirmed baseline integrity by running the full test suite (100 tests passing) before proceeding.

## 5. Architectural Boundaries Upheld

The brief explicitly prohibited several patterns. All were respected:

| Prohibition | Compliance |
|---|---|
| ❌ Simultaneous multipath transfer | Single active carrier at a time; migration swaps carriers sequentially. |
| ❌ Internet failover / NAT traversal / STUN / TURN / QUIC | None introduced; still LAN-focused TCP. |
| ❌ New transport abstraction | Reused `Transport` trait and `TcpTransport` unchanged. |
| ❌ New path-health subsystem | `TransferCarrier` is a *consumer* of `PathRegistry`, `PathSelector`, and `PathHealthMonitor` — not a replacement. |
| ❌ Gateway-driven migration | Migration logic lives entirely in `flux-core`; Gateway unchanged. |
| ❌ New wire protocol messages | Zero changes to `FluxMessage`. Reused existing `TransferResume` semantics for chunk-level continuation. |

## 8. Observations & Recommendations for S3.7

### 8.1 File-Level Checkpoint Granularity

The current implementation checkpoints at **file boundaries** — if a 1 GB file fails at 500 MB, the entire file restarts on the new carrier (though the receiver's chunk-level `.part` state still provides intra-file resumption via `TransferResume`). This is correct and safe, but future sprints could introduce **chunk-level migration checkpointing** on the sender side to avoid re-reading already-transmitted chunks after migration.

### 8.2 Carrier Lifecycle in Gateway

The Gateway currently uses `send_collection_with_cancel_and_progress` directly on a `Session`. It does **not yet** use `TransferCarrier`. This was a deliberate boundary preservation — introducing the carrier into the Gateway would require architectural decisions about how the Gateway holds `Arc<TcpTransport>` and `PathRegistry` references, which is outside S3.6 scope.

A follow-up sprint (S3.7 or S3.8) should integrate `TransferCarrier` into the Gateway's `start_transfer` flow, enabling autonomous migration for HTTP-initiated transfers. The existing `attach_continuation` method in `GatewayTransferTracker` provides the right hook.

### 8.3 Replacement Path Failure Cascading

Currently, if a replacement path connection fails, the carrier enters `Failed` state. A future enhancement could implement **cascading retry** — select the next-next-best path and retry up to a configurable limit. The `migration_count` field already tracks attempts; a `max_migrations: usize` configuration field would complete this.

### 8.4 Concurrent Migration Safety

`TransferCarrier::migrate()` takes `&mut self`, so Rust's borrow checker guarantees no concurrent migration calls on the same carrier. If future work introduces shared carrier access (e.g., via `Arc<Mutex<TransferCarrier>>`), the race condition noted in the brief's §14 would need explicit handling — currently prevented by ownership.

### 8.5 Simultaneous Multipath

S3.7 should begin design discussions for **simultaneous multipath transfer** (concurrent chunk striping across paths), which is explicitly out of scope for S3.6 but is the natural next evolution of the carrier abstraction.
