## 1. Executive Summary

Sprint S3.9 extends Flux's autonomous transfer migration architecture, originally introduced in S3.6 and enhanced in S3.8, to support **cascading multi-path fallback recovery**. Prior to this sprint, a transfer could survive exactly **one** path failure. If the replacement candidate was also unreachable (either because its connection setup failed or because the next active transfer broke it), the entire transfer terminated.

With S3.9, a single logical transfer can now autonomously traverse an arbitrary number of sequential path failures (`Path A → Path B → Path C → Path D → …`), as well as fall through to the next candidate when a replacement connection itself fails. The transfer identity, chunk checkpointing semantics, receiver `.part` authority, cancellation precedence, and Gateway abstraction boundary all remain fully intact.

**No wire protocol modifications were required. No new public APIs were introduced. No parallel migration subsystem was created.** The entire sprint was implemented as a disciplined extension of the existing `TransferCarrier::migrate()` method.

## 2. Problem Statement

### Pre-S3.9 Behavior

The S3.6/S3.7 autonomous migration mechanism had a strict single-shot contract:

```
Path A → fails → migrate() → Path B
                  ↓
                  success → Active(B)
                  failure → Err → Transfer terminates
```

If `Path B` could not be reached during replacement, the `?` operator in `TransferManager::send_collection_with_carrier()` propagated the failure to the caller, surfacing the transfer as `Err(Transport(_))` even if `Path C` and `Path D` were perfectly healthy in the `PathRegistry`.

### Target Behavior

A logical transfer must survive:
1. Multiple sequential path failures during active transmission.
2. Replacement connection failures during the migration handshake itself.
3. Full candidate exhaustion must terminate cleanly without panic, infinite loop, or progress corruption.

Before writing any code, we performed a thorough architecture survey using PowerShell inspection of the critical files:

### Key Findings
- The `MigrationState` enum already contained a `migration_count` field — repeated migrations were legal state-machine-wise.
- `PathSelector::select_path()` filters strictly on `PathState::Available` — no API changes needed if we marked failed candidates as `Unavailable` in `PathRegistry`.
- `ChunkCheckpoint` was already managed in `manager.rs` outside `migrate()`, so it survived naturally across migrations.
- The receiver's `.part`/`.part.meta` resume authority was fully protocol-compatible with repeated migrations.

### Deliverables Produced
- `docs/s3_9_investigation.md` — architectural investigation note
- `docs/decisions/0017-cascading-path-migration.md` — formal ADR documenting the design decision

**Conclusion:** The architecture was fundamentally sufficient. The only required change was converting `migrate()` from a single-shot operation into an internal candidate retry loop.

## 4. Implementation Details

### 4.1 Core Change — `TransferCarrier::migrate()`

The method signature remained **unchanged**:
```rust
pub async fn migrate(&mut self) -> Result<()>
```

The internal structure changed from a linear flow:
```
mark failed path Unavailable
→ select ONE candidate
→ connect → return Ok or Err
```

To a cascading loop:
```
mark failed path Unavailable
→ shutdown broken session
→ loop {
    select next best candidate
    if none → Err (Paused state)
    attempt connect
    if success → install session, return Ok
    if failure → mark candidate Unavailable, continue
  }
```

### 4.2 Why the Existing Abstractions Were Sufficient

- **`PathRegistry::set_path_state()`** was already thread-safe and shared via `Arc<RwLock<_>>`.
- **`PathSelector::select_path()`** filtered on `PathState::Available`, so marking a failed candidate as `Unavailable` naturally excluded it from subsequent selections.
- **`TransferManager`'s loop** was already defensive — it caught `TransferError::Transport(_)`, checked cancellation, called `carrier.migrate().await?`, and then retried the current chunk. No changes needed.
- **Receiver's `.part.meta`** already authoritatively drove resume via `FluxMessage::TransferResume`, which was reused unchanged.

### 4.3 Loop Termination Guarantee

Infinite migration loops are structurally impossible:
1. Each connection failure marks the candidate as `Unavailable` in the shared registry.
2. `PathSelector` only returns `Available` paths.
3. Since the registry contains a finite path set, the loop always terminates — either successfully on a healthy candidate or with `MigrationState::Paused` when `select_path()` returns `None`.

## 5. Problems Encountered & Mitigations

### 5.1 Compilation: `tracing` Not In Dependencies
**Issue:** Initial implementation imported `tracing::{error, info, warn}`.
**Mitigation:** Workspace uses the `log` crate consistently. Switched to `use log::{error, info, warn}`.

### 5.2 Compilation: `PeerId` Private Re-export
**Issue:** `use crate::peer::PeerId` failed because `peer::mod.rs` re-imports `PeerId` without `pub`.
**Mitigation:** Switched to the canonical path `use crate::identity::PeerId`, matching the pattern used elsewhere in the codebase.

### 5.3 E2E Test: Multi-Hop Receiver's `Option<FileReceiver>`
**Issue:** `FileReceiver::try_resume()` returns `Result<Option<FileReceiver>>`, not `Result<FileReceiver>`. The test code called `.resume_from_chunk()` directly on the `Option`.
**Mitigation:** Added `.expect("Receiver B should find partial file state")` to unwrap the `Option` explicitly where partial state was guaranteed to exist.

### 5.4 E2E Test: Hung Test Due to RTT-Driven Candidate Selection
**Issue:** The first draft of `test_s39_e2e_double_migration_cascade` set:
- Path A: 150 ms
- Path B: 100 ms
- Path C: 50 ms

Because `PathSelector` picks the lowest RTT, after Path A failed the sender jumped directly to **Path C** (50 ms, best candidate), bypassing Path B entirely. The test hung because `receiver_handle_b` was blocked indefinitely on `listener_b.accept()`.

**Root Cause:** We assumed migration order followed path registration order; in reality it follows RTT ranking.

**Mitigation:** Rebalanced RTT values so each path becomes the best remaining candidate after the previous one fails:
- Path A: 150 ms (initial)
- Path B: 50 ms (best when A fails)
- Path C: 100 ms (best when B fails)

For the quadruple-cascade test, the same principle was applied with four values: 200/30/60/90 ms.

### 5.5 E2E Test: Protocol Message Mismatch (`TransferAccept` vs `TransferResult`)
**Issue:** In `test_s39_e2e_multi_file_cascading_migration`, after Receiver B finished File 1, we incorrectly replied with `TransferAccept` to the `TransferComplete` message. The sender expected `TransferResult`, causing:
```
UnexpectedMessage("Expected TransferResult, got TransferAccept { ... }")
```

**Mitigation:** Reviewed `TransferManager::send_file_internal()` protocol expectations. Corrected the test receiver to reply with:
```rust
FluxMessage::TransferResult {
    transfer_id: metadata.transfer_id,
    success: true,
    message: "File 1 verified".to_string(),
}
```
Note: `message` is a `String`, not an `Option<String>` — a subtle field type we discovered through the compiler error.

### 5.6 Formatting Diffs
**Issue:** `cargo fmt --check` surfaced long lines, chained `.await.unwrap()` method calls, missing newlines after assertions, and import grouping differences.
**Mitigation:** Ran `cargo fmt` once to normalize across all affected files, then re-ran `cargo fmt --check` to confirm clean state.

## 11. Key Design Lesson Internalized

> **S3.6** taught Flux: *a transfer can migrate.*
> **S3.8** taught Flux: *a transfer can migrate efficiently without retransmitting completed chunks.*
> **S3.9** teaches Flux: *migration itself is repeatable and resilient; a transfer is not tied to any single path or single migration event.*

The S3.9 architectural win is not that we added "fallback logic" — it is that **we didn't add a parallel migration subsystem**. The existing abstractions (`TransferCarrier`, `PathSelector`, `PathRegistry`, `ChunkCheckpoint`, `FileReceiver::try_resume`) were already composable enough to support cascading recovery with a minimal, targeted change inside one method.

**One logical transfer. Multiple interchangeable carriers. Arbitrarily many sequential migrations until the available path set is exhausted.**
