## 1. Executive Summary

Sprint 1.5 delivers interruptible, resumable file transfers in Aryntra Flux. When a connection drops mid-transfer, the receiver preserves the already-received data and metadata. On reconnection, the receiver informs the sender of the last successfully persisted chunk, and the sender resumes from that point — without retransmitting data the receiver already has.

The implementation adds resume state persistence, a single new protocol message, chunker seeking, and resume negotiation orchestration. All changes are strictly above the Session layer. The existing S1.4 transfer flow is preserved as the default path when no partial state exists.

## 3. Protocol Design

### 3.1 New Message Variant

One new variant was appended to the existing `FluxMessage` enum. No existing variants were modified or removed.

| Variant | Direction | Purpose |
|---|---|---|
| `TransferResume { transfer_id, resume_from_chunk }` | Receiver → Sender | Informs sender that partial state exists and specifies the chunk index to resume from |

This variant is serialized through the existing `bincode` + 4-byte length-prefix framing. No new framing layer was introduced.

### 3.3 Design Rationale

**Why match on file metadata instead of TransferId?** `TransferMetadata::new()` generates a fresh UUID-v4 `transfer_id` on every call. A reconnection creates a new `TransferRequest` with a new ID. Resume matching therefore uses the stable tuple `(file_name, file_size, chunk_size, total_chunks, sha256)` to identify whether a partial file corresponds to the incoming transfer.

**Why sequential chunk-boundary resume?** The existing S1.4 protocol is strictly sequential. Introducing sparse chunk maps or parallel chunk tracking would add significant complexity for no benefit over a single TCP stream. Sequential resume from the highest contiguous chunk is correct, simple, and sufficient.

**Why disk-based SHA-256 at finalization?** The S1.4 receiver computed SHA-256 incrementally as chunks arrived. For resumed transfers, the incremental hasher would need to be reconstructed from the existing `.part` data. Computing the hash from the complete file on disk at finalization produces the same result, works identically for both fresh and resumed transfers, and avoids the complexity of persisting/restoring hasher state.

**Why `.part.meta` sidecar instead of embedding in the `.part` file?** Keeping metadata separate avoids modifying the binary data file format, allows atomic metadata updates via rename, and makes it trivial to inspect or debug partial transfer state.

## 4. Security & Safety

### 4.1 Five-Point Resume Validation

Before resuming, `FileReceiver::try_resume()` verifies:

1. **File name match** — partial state filename equals incoming metadata filename.
2. **File size match** — expected total bytes are identical.
3. **Chunk size match** — chunk boundaries must align.
4. **Total chunks match** — derived from file_size and chunk_size.
5. **SHA-256 match** — expected hash of the complete file is identical.
6. **Physical size match** — actual `.part` file size on disk equals `bytes_received` in the metadata.

If any check fails, the partial state is purged and a fresh transfer begins.

### 4.2 Write-Then-Record Ordering

Chunks are written and flushed to the `.part` file **before** the `.part.meta` state is updated. This ensures that a crash between the data write and the metadata update results in a conservative (slightly behind) resume point rather than a false horizon that would skip un-persisted data.

### 4.3 Atomic Metadata Updates

The `.part.meta` file is written to a `.part.meta.tmp` temporary file first, then atomically renamed. This prevents a mid-write crash from producing a corrupt metadata file that could mislead the resume logic.

### 4.4 Corrupt State Cleanup

When `try_resume()` detects a deserialization failure, metadata mismatch, or physical size discrepancy, it automatically deletes both the `.part` and `.part.meta` files before returning `None`. This ensures that corrupt partial state never persists across multiple reconnection attempts.

### 4.5 Integrity Guarantees Preserved

The S1.4 triple-point verification (chunk sequence + byte count + SHA-256) remains mandatory at finalization. Resume does not weaken any integrity guarantee.

## 6. Known Limitations & Deferred Work

| Capability | Rationale for Deferral |
|---|---|
| Parallel chunk transmission | Sequential is correct over single TCP; parallelism adds complexity without throughput benefit |
| Sparse chunk maps | Sequential contiguous resume is sufficient; sparse maps needed only for multi-path or unreliable transports |
| Adaptive chunk sizing | Fixed 64 KiB is safe and predictable; tuning requires bandwidth estimation |
| Cross-session transfer ID tracking | Resume matches on file metadata, not transfer ID; a future transfer registry could enable richer matching |
| Compression | Adds CPU cost; should be evaluated after baseline transfer is stable |
| Multi-file / directory transfer | Single-file is the atomic primitive; directory sync builds on top |
| GUI | CLI is the target interface for the current development phase |
