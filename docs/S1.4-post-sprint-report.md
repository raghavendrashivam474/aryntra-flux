## 1. Executive Summary

Sprint 1.4 delivers the first end-to-end file transfer capability in Aryntra Flux. A sender node can now stream an arbitrary file to a receiver node over the existing TCP/session infrastructure, with the receiver reconstructing the file byte-for-byte and verifying its integrity via SHA-256.

The implementation adds a new `transfer` module strictly above the Session layer, leaving all S1.3 transport, protocol framing, session lifecycle, discovery, and identity code untouched. The feature is exposed through a new `flux send` CLI command and an enhanced listener that auto-detects incoming transfer requests.

## 2. Architecture

### 2.1 Layering

The central architectural constraint of S1.4 is that **file transfer logic does not penetrate the Session or Transport layers**. The layering is as follows:

```
┌─────────────────────────────────┐
│          CLI (flux-node)        │  ← User-facing commands
├─────────────────────────────────┤
│      TransferManager            │  ← S1.4: orchestrates send/receive
│   ┌───────────┬───────────┐     │
│   │  Chunker  │ Receiver  │     │  ← S1.4: streaming I/O + verification
│   └───────────┴───────────┘     │
├─────────────────────────────────┤
│          Session                │  ← S1.3: identity-verified channel
├─────────────────────────────────┤
│     Protocol (FluxMessage)      │  ← S1.3 + S1.4 extended variants
├─────────────────────────────────┤
│       Transport (TCP)           │  ← S1.3: framed, length-prefixed
├─────────────────────────────────┤
│    Discovery / Identity         │  ← S1.1–S1.2: mDNS, PeerId
└─────────────────────────────────┘
```

The `TransferManager` communicates exclusively through `Session::send_message()` and `Session::recv_message()`. It has no dependency on `TcpTransport`, `TcpConnection`, or any socket-level API. This means the transfer layer will work unchanged when future transports (QUIC, Bluetooth, relay) are added.

### 2.2 Module Structure

```
crates/flux-core/src/transfer/
├── mod.rs          # Module root, re-exports public API
├── error.rs        # TransferError enum (thiserror-based)
├── metadata.rs     # TransferMetadata struct, TransferId type alias
├── chunker.rs      # Async streaming file reader (sender-side)
├── receiver.rs     # Async file reassembler with verification (receiver-side)
└── manager.rs      # High-level send_file() and receive_transfer() orchestration
```

## 3. Protocol Design

### 3.1 Message Extensions

Six new variants were added to the existing `FluxMessage` enum. No existing variants were modified or removed, preserving full backward compatibility with S1.3 nodes for non-transfer messages.

| Variant | Direction | Purpose |
|---|---|---|
| `TransferRequest { metadata }` | Sender → Receiver | Initiates transfer with file name, size, chunk count, SHA-256 |
| `TransferAccept { transfer_id }` | Receiver → Sender | Confirms willingness to receive |
| `TransferReject { transfer_id, reason }` | Receiver → Sender | Declines transfer with human-readable reason |
| `TransferChunk { transfer_id, index, data }` | Sender → Receiver | Carries one 64 KiB chunk with explicit sequence index |
| `TransferComplete { transfer_id }` | Sender → Receiver | Signals all chunks have been sent |
| `TransferResult { transfer_id, success, message }` | Receiver → Sender | Reports final verification outcome |

All variants are serialized through the existing `bincode` + 4-byte length-prefix framing. No new framing layer was introduced.

### 3.2 Transfer Flow

```
Sender                                    Receiver
  │                                          │
  │── TransferRequest(metadata) ────────────>│  Validate metadata, create .part file
  │                                          │
  │<── TransferAccept(transfer_id) ─────────│
  │                                          │
  │── TransferChunk(id, 0, data) ──────────>│  Write chunk 0, update running SHA-256
  │── TransferChunk(id, 1, data) ──────────>│  Write chunk 1
  │── ...                                    │  ...
  │── TransferChunk(id, N, data) ──────────>│  Write chunk N
  │                                          │
  │── TransferComplete(id) ────────────────>│  Finalize: check size, verify SHA-256
  │                                          │  Rename .part → final (or delete on failure)
  │<── TransferResult(id, success, msg) ────│
  │                                          │
```

### 3.3 Design Rationale

**Why no per-chunk ACKs?** The underlying transport is TCP, which already guarantees ordered, reliable delivery. Adding application-level ACKs would duplicate TCP's retransmission logic and add latency for no reliability gain. This decision is documented in ADR-007 and should be revisited only when unreliable transports (UDP, Bluetooth) are introduced.

**Why explicit chunk indices despite TCP ordering?** Carrying the index makes the protocol self-describing and transport-agnostic. When a future unreliable transport is added, the index will be essential for reordering. It also enables the receiver to detect protocol-level anomalies (e.g., a duplicated or skipped chunk due to a bug) even over TCP.

**Why a fixed 64 KiB chunk size?** This keeps every `TransferChunk` message well under the existing 1 MB frame guard (64 KiB payload + ~50 bytes of metadata overhead). It also provides a constant, predictable memory footprint. Adaptive chunk sizing is explicitly deferred to a future sprint.

## 4. Security & Safety

### 4.1 Path Traversal Protection

The `FileReceiver::sanitize_filename()` function rejects any filename containing:

- `..` (parent directory traversal)
- `/` or `\` (path separators)
- Absolute path prefixes (e.g., `C:` on Windows, `/` on Unix)
- Characters outside `[a-zA-Z0-9._-]`

All received files are confined to the `received/` directory relative to the working directory. A malicious peer cannot write to arbitrary filesystem locations.

### 4.2 Partial File Isolation

Incoming data is written to a `.part` temporary file (e.g., `received/document.pdf.part`). The final file is only created via atomic rename after all three verification checks pass. If the transfer fails at any point, the `.part` file is deleted. This prevents incomplete or corrupted files from being mistaken for valid data.

### 4.3 Triple-Point Verification

Before a transfer is declared successful, the receiver verifies:

1. **Chunk sequence integrity** — each chunk's index matches the expected sequential position.
2. **Byte count** — total received bytes equal `metadata.file_size`.
3. **SHA-256 hash** — the running hash of all received bytes matches `metadata.sha256`.

A transfer that passes chunk count but fails hash verification (e.g., due to a bit-flip or a malicious sender) is rejected and the `.part` file is purged.

### 4.4 Memory Safety

Both the `Chunker` (sender) and `FileReceiver` (receiver) use bounded 64 KiB buffers. A 10 GB file transfer consumes no more than ~64 KiB of heap memory at any point. The file is never loaded into RAM in its entirety.

## 6. CLI Integration

### 6.1 New Command

```
flux send --addr <IP:PORT> --file <path>
```

Establishes a session with the target node, negotiates the transfer, streams chunks with progress output, and reports the final result.

### 6.2 Enhanced Listener

The existing `flux listen` command now inspects the first message received on each connection:

- If it is a `Ping`, the listener responds with a `Pong` (S1.3 behavior, unchanged).
- If it is a `TransferRequest`, the listener hands the connection to `TransferManager::receive_transfer()`.
- Other message types are logged and the connection is closed.

This design allows a single listening node to handle both S1.3 pings and S1.4 transfers without separate ports or configuration.

## 7. Known Limitations & Deferred Work

The following capabilities are **explicitly out of scope** for S1.4 and should not be considered defects:

| Capability | Rationale for Deferral |
|---|---|
| Transfer resume | Requires persistent chunk-offset tracking; planned for S1.5 |
| Parallel chunk transmission | Sequential is correct and simpler; parallelism adds complexity without benefit over single TCP stream |
| Adaptive chunk sizing | Fixed 64 KiB is safe and predictable; tuning requires bandwidth estimation infrastructure |
| Compression | Adds CPU cost; should be evaluated after baseline transfer is stable |
| Encryption redesign | S1.4 operates over the existing session; encryption is a separate architectural concern |
| Multi-file / directory transfer | Single-file is the atomic primitive; directory sync builds on top |
| Transfer rate limiting | No backpressure mechanism yet; TCP flow control is sufficient for S1.4 |
| GUI | CLI is the target interface for the current development phase |

## 9. Recommendations for S1.5

Based on the architecture established in S1.4, the natural next steps are:

1. **Transfer Resume (S1.5-A):** Persist chunk-offset state so that interrupted transfers can skip already-received chunks. The `TransferId` and chunk indexing infrastructure is already in place to support this.

2. **Multi-File Transfer (S1.5-B):** Extend `TransferRequest` to carry a manifest of files, or introduce a directory-walking sender that initiates sequential transfers over a single session.

3. **Transfer Multiplexing (S1.5-C):** Allow multiple concurrent transfers over a single session by dispatching on `TransferId` at the `TransferManager` level.

4. **Backpressure & Rate Limiting (S1.5-D):** Introduce receiver-side flow control to prevent fast senders from overwhelming slow receivers or constrained networks.
