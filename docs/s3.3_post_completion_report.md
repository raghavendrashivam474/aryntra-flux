Sprint S3.3 replaces the raw tokio task-abort cancellation mechanism from S3.2 with a **cooperative, wire-level transfer cancellation protocol** and establishes the foundational control boundary required for future path-aware transfer continuity (S3.5) and adaptive path migration (S3.6).

## 3. Implementation Details

### 3.1 Protocol Layer — `crates/flux-core/src/protocol/message.rs`

**What:** Added `TransferCancel { transfer_id: TransferId }` variant to the `FluxMessage` enum under a new `// --- S3.3: Transfer control messages ---` section.

**How:** The variant follows the exact same structural pattern as `TransferComplete` and `TransferAccept` — a single `TransferId` field. Since `FluxMessage` derives `Serialize, Deserialize, PartialEq` via `serde` + `bincode`, the new variant is automatically wire-compatible with the existing length-prefix framing. No changes to `framing.rs` were required.

**Test:** `test_transfer_cancel_serialize` round-trips a `TransferCancel` through `encode_message` → `decode_message(&encoded[4..])` and asserts equality, matching the pattern of the existing `test_transfer_resume_serialize` test.

### 3.2 Error Layer — `crates/flux-core/src/transfer/error.rs`

**What:** Added `TransferError::Cancelled` variant with `#[error("Transfer cancelled")]` display.

**How:** This is a unit variant (no payload) because cancellation is a deliberate control signal, not a failure condition requiring diagnostic context. The `TransferManager` returns `Err(TransferError::Cancelled)` from all cancellation exit points, allowing callers (including the Gateway) to pattern-match on it explicitly.

### 3.3 Cancellation Token — `crates/flux-core/src/transfer/control.rs` (New File)

**What:** `TransferCancellation` — a thread-safe, cloneable, cooperative cancellation handle built on `Arc<AtomicBool>`.

**How:** Three methods:
- `new()` — creates a non-cancelled token.
- `cancel()` — sets the atomic flag via `SeqCst` ordering.
- `is_cancelled()` — reads the atomic flag.

The token is `Clone` (via `Arc`) so it can be shared between the Gateway's HTTP handler thread and the tokio task running the actual transfer. When the Gateway's `POST /cancel` endpoint is hit, it calls `cancel()` on the token, and the transfer loop observes `is_cancelled()` on its next iteration.

**Design rationale:** We chose a simple `AtomicBool` over `tokio_util::sync::CancellationToken` because:
1. `tokio-util` is not currently a workspace dependency.
2. The transfer loops are synchronous-check (poll-based between chunks), not async-await-select-based, so we don't need the `cancelled()` future.
3. The `AtomicBool` approach is zero-dependency, trivially testable, and sufficient for the current chunk-boundary polling model.

If S3.4 or S3.5 introduces `tokio::select!`-based transfer loops, this can be upgraded to `CancellationToken` with a documented ADR at that time.

### 3.4 Transfer Manager — `crates/flux-core/src/transfer/manager.rs`

**What:** All four public entry points (`send_file`, `send_collection`, `receive_transfer`, `receive_collection`) now accept an optional `TransferCancellation` token via new `*_with_cancel` variants. The original methods delegate to the `*_with_cancel` variants with a fresh, never-cancelled token, preserving 100% backward compatibility.

**How — Sender side (`send_file_internal`):**
1. Check `cancel.is_cancelled()` at function entry (handles pre-transfer cancellation).
2. Handle incoming `FluxMessage::TransferCancel` in the accept/reject/resume match arm.
3. Check `cancel.is_cancelled()` inside the chunk transmission loop, before each `send_message`. If triggered, send `TransferCancel` over the wire to the receiver and return `Err(Cancelled)`.
4. Check again before sending `TransferComplete`.
5. Handle `TransferCancel` in the final result-wait match arm.

**How — Receiver side (`receive_transfer_with_cancel`):**
1. Check `cancel.is_cancelled()` inside the chunk reception loop, before each `recv_message`. If triggered, send `TransferCancel` to the sender and return `Err(Cancelled)`. The `FileReceiver` is dropped naturally, **leaving `.part` and `.part.meta` intact on disk**.
2. Handle incoming `FluxMessage::TransferCancel` in the chunk match arm and the completion-wait match arm.
3. Check again before finalization.

**Critical design point:** The receiver **never** calls `fs::remove_file` on `.part` or `.part.meta` during cancellation. The `FileReceiver` struct is simply dropped, which closes the file handle but does not delete the partial data. This is what enables resume-after-cancellation.

### 3.5 Session Lifecycle — `crates/flux-core/src/session.rs`

**What:** Added `Session::shutdown(&mut self) -> Result<()>` and `Session::is_established() -> bool`.

**How:** `shutdown()` is non-consuming (takes `&mut self`), transitions state to `Closing`, sends a `Goodbye` message (ignoring send errors since the connection may already be degraded), and transitions to `Closed`. It is idempotent — calling it on an already-closed session is a no-op.

**Distinction from `close(self)`:**
- `close(self)` consumes ownership, sends `Goodbye`, calls `connection.close()` (which shuts down the TCP stream), and is terminal.
- `shutdown(&mut self)` borrows mutably, sends `Goodbye`, marks state as `Closed`, but does **not** tear down the underlying transport. This allows the session to remain in the Gateway's session pool for potential reuse.

**Test:** `test_session_shutdown` verifies the full lifecycle: established → shutdown → state is `Closed` → repeated shutdown is idempotent → send/recv on closed session returns errors.

### 3.6 Gateway Tracker — `crates/flux-gateway/src/transfer_tracker.rs`

**What:** `ActiveTransfer` now holds a `TransferCancellation` token alongside the existing `JoinHandle`. The `register()` method accepts the token as a new parameter. The `cancel()` method triggers `cancel_token.cancel()` instead of `handle.abort()`.

**Lifecycle guards added:**
- `mark_completed()` only transitions from `Running`/`Created`.
- `mark_failed()` only transitions from `Running`/`Created`.
- `cancel()` only transitions from `Running`/`Created`.
- Terminal states (`Completed`, `Failed`, `Cancelled`) are immutable.

### 3.7 Gateway Routes — `crates/flux-gateway/src/routes/transfer.rs`

**What:** `start_transfer` now creates a `TransferCancellation::new()`, clones it into the spawned task, and passes it to `TransferManager::send_collection_with_cancel`. The task match arm explicitly handles `TransferError::Cancelled` and calls `tracker.mark_cancelled()`.

**How:** The `cancel_transfer` endpoint's implementation did not change at the HTTP layer — it still calls `state.tracker.cancel(&transfer_id)`. But the tracker's `cancel()` method now triggers the cooperative token instead of aborting the task handle. The task handle is still stored for potential future use (e.g., timeout enforcement) but is no longer the primary cancellation mechanism.

### 3.8 Module Exports — `crates/flux-core/src/transfer/mod.rs`

**What:** Registered `pub mod control` and `pub use control::TransferCancellation`.

## 4. Problems Encountered and Mitigations

### Problem 1: UTF-8 BOM Corruption of Rust Source Files

**Symptom:** After writing `transfer/mod.rs` via PowerShell's `Set-Content`, the Rust compiler reported `E0432: unresolved imports` for symbols that clearly existed in the file.

**Root cause:** PowerShell's default `Set-Content` encoding on Windows writes UTF-8 with a Byte Order Mark (BOM: `EF BB BF`). The Rust compiler treats the BOM as invalid syntax at the start of the file, silently corrupting the first `use` statement.

**Mitigation:** Switched all file writes to `[System.IO.File]::WriteAllText($path, $content, (New-Object System.Text.UTF8Encoding $false))`, which writes UTF-8 without BOM. Applied this consistently across all subsequent blocks.

**Lesson:** On Windows, never use PowerShell's `Set-Content` or `Out-File` for source code files. Always use .NET's `WriteAllText` with explicit BOM-less UTF-8.

---

### Problem 2: Trailing Semicolon on Return Expression in `control.rs`

**Symptom:** `error[E0308]: mismatched types — expected bool, found ()` on `is_cancelled()`.

**Root cause:** The line `self.cancelled.load(Ordering::SeqCst);` had a trailing semicolon, making it a statement rather than a tail expression. The function implicitly returned `()`.

**Mitigation:** Removed the semicolon. This is a classic Rust gotcha — the compiler error message was clear and the fix was trivial.

**Lesson:** When writing single-expression functions in Rust, always verify the absence of trailing semicolons. The compiler catches this, but it wastes a build cycle.

---

### Problem 3: Dropped Re-exports in `transfer/mod.rs`

**Symptom:** `error[E0432]: unresolved imports transfer::CollectionError, transfer::TransferItem` in `lib.rs`.

**Root cause:** When rewriting `transfer/mod.rs` to add `pub mod control`, I initially only included the re-exports I knew about (`TransferManager`, `TransferMetadata`, etc.) and omitted `CollectionError`, `TransferItem`, and `sanitize_relative_path`, which were re-exported by `lib.rs` line 25.

**Mitigation:** Inspected `crates/flux-core/src/lib.rs` with `Select-String` to discover the exact re-export list, then restored all original exports alongside the new `TransferCancellation` export.

**Lesson:** When modifying a `mod.rs` that serves as a public API surface, always cross-reference the parent module's `pub use` statements to ensure no re-exports are silently dropped.

---

### Problem 4: Gateway `register()` Signature Change Broke Integration Tests

**Symptom:** `error[E0061]: this method takes 6 arguments but 5 arguments were supplied` in `crates/flux-gateway/tests/integration.rs`.

**Root cause:** Adding `cancel_token: TransferCancellation` to `ActiveTransfer` changed `register()` from 5 to 6 parameters. The existing integration test at line 164 still called it with 5 arguments.

**Mitigation:** Updated the test to pass `TransferCancellation::new()` as the 5th argument. This also served as validation that the new parameter integrates cleanly with existing test infrastructure.

---

### Problem 5: Missing TCP Server Handshake in E2E Cancellation Tests

**Symptom:** Both `test_e2e_cancellation_pre_transfer` and `test_e2e_cancellation_preserves_partial_state_and_resumes` panicked with `HandshakeFailed("Expected HelloAck")`.

**Root cause:** The test receiver spawned a task that called `listener.accept()` and immediately wrapped the raw connection in `Session::from_connection()`. However, the Flux TCP transport requires an explicit `server_handshake()` call on the accepted `TcpConnection` before the session can exchange messages. The existing e2e tests (e.g., `test_e2e_tcp_file_transfer`) perform this handshake via `conn.as_any_mut().downcast_mut::<TcpConnection>()`, but my initial test code omitted this step.

**Mitigation:** Inspected the existing `test_e2e_tcp_file_transfer` test to discover the correct pattern, then added the `downcast_mut::<TcpConnection>()` + `server_handshake()` sequence to both new tests.

**Lesson:** The Flux test infrastructure does not auto-handshake on accept. Every test that creates a server-side connection must manually invoke `server_handshake()`. This is a consequence of the transport abstraction design — the `Listener` trait returns a raw `Connection`, and the handshake is a TCP-specific concern.

---

### Problem 6: Clippy `cloned_ref_to_slice_refs` Lint

**Symptom:** `error: unnecessary use of clone to create a slice from a reference` on `&[file_path.clone()]`.

**Root cause:** Clippy 1.97 flags `&[x.clone()]` when `x` is already a reference, recommending `std::slice::from_ref(&x)` instead.

**Mitigation:** Replaced `&[file_path.clone()]` with `std::slice::from_ref(&file_path)`.

---

### Problem 7: Incorrect `Peer` Constructor in Rewritten Integration Tests

**Symptom:** `error[E0599]: no associated function or constant named new found for struct Peer` and `error[E0609]: no field peer_registry on type Arc<FluxNode>`.

**Root cause:** When rewriting `integration.rs` to add cancellation tests, I inadvertently rewrote the existing `test_peers_empty_and_retrieval` test using an incorrect `Peer::new()` constructor and `node.peer_registry` field name. The actual API uses struct literal construction (`Peer { id, address, last_seen }`) and `node.registry`.

**Mitigation:** Ran `git checkout HEAD -- crates/flux-gateway/tests/integration.rs` to restore the original file, then carefully applied only the two targeted changes: (1) adding `TransferCancellation::new()` to the existing `register()` call, and (2) appending the new `test_gateway_transfer_cancel_lifecycle` test at the end of the file.

**Lesson:** When modifying test files, prefer surgical edits over full rewrites. The original tests encode institutional knowledge about the exact API surface that may not be obvious from reading the source.

## 7. Architectural Decision Record

**ADR-0012: Cooperative Transfer Cancellation and Session Control** has been written to `docs/decisions/0012-reliable-transfer-control.md` documenting the rationale for:
1. Wire-level `TransferCancel` over raw task abortion.
2. `AtomicBool`-based cancellation tokens over `tokio_util::CancellationToken`.
3. Non-consuming `Session::shutdown(&mut self)` alongside consuming `Session::close(self)`.
4. Explicit partial state preservation on cancellation.

## 8. Forward-Looking Notes for S3.4 and S3.5

1. **S3.4 (Transfer Observability):** The `TransferCancellation` token and deterministic lifecycle states (`CREATED/RUNNING/COMPLETED/FAILED/CANCELLED`) provide the exact hooks needed for progress reporting and WebSocket streaming. The `TransferManager`'s chunk-boundary polling points are natural places to emit progress events.

2. **S3.5 (Path-Aware Transfer Continuity):** The key architectural invariant established in S3.3 — that a transfer is a logical operation independent of its underlying session — is the prerequisite for path migration. When a path fails mid-transfer in S3.5, the transfer can remain alive while a new session is established over an alternate path, resuming from the preserved `.part` state.

3. **Potential future upgrade:** If S3.5 introduces `tokio::select!`-based transfer loops (e.g., racing chunk transmission against path health events), the `TransferCancellation` token may need to be upgraded to `tokio_util::sync::CancellationToken` to support `.cancelled()` as a future. This should be documented with a new ADR at that time.
